# 多人联机开发方案

> 类银河恶魔城 Unity 2D 动作RPG — 毕设项目  
> **网络方案**：自研 LiteNetLib（源码编译）+ 自研 Unity 网络层（游戏对象同步）  
> **联机模式**：Listen Server（主机模式），纯单机模式保留  
> **传输切换**：自研 LiteNetLib（局域网/直连）↔ Steamworks（大厅/P2P）  
> **时间预算**：5 个月以上  
> **当前进度**：阶段一 ✅ | 阶段二 ✅ | 聊天系统 ✅ | 阶段三（待开始）

## 二、关键设计决策

| 序号 | 决策 | 选择 |
|------|------|------|
| 1 | 传输抽象方式 | `IGameTransport` 接口 |
| 2 | RPC 风格 | 直接 PackMessage + Send / Dispatcher，不做额外封装层 |
| 3 | 网络库方式 | **源码直接编译**（去 DLL），避免版本不一致 |
| 4 | 聊天消息 | 每条消息一个独立预制体，ContentSizeFitter + VerticalLayoutGroup 自动排列 |
| 5 | 玩家编号 | 服务端按连接顺序自动分配（玩家1/2/3/4...，带颜色） |
| 6 | 输入屏蔽 | GameInput 统一切口，聊天打开时全部返回 false |
| 7 | 位置同步 | 服务端快照 + 客户端插值（预测可选延迟） |
| 8 | 背包模型 | 简化版：各客户端管理自己背包，只广播变化 |
| 9 | 服务端AI | 是，Enemy 在服务端（主机）跑完整 FSM |
| 10 | 伤害计算 | 服务端执行，广播结果 |
| 11 | 客户端预测 | 阶段三可选 |
| 12 | 断线重连 | 不实现（显示"主机已断开"即可） |
| 13 | 主机迁移 | 不实现 |
| 14 | 防作弊 | 有限——Listen Server 模式下信任主机 |

## 四、已修复的问题

| # | 问题 | 修复 |
|---|------|------|
| 1 | DLL 版本不一致导致 Build 打包后 PackMessage 重载解析错误 | LiteNetLib 改为源码直接编译，去 DLL 化 |
| 2 | 关闭程序时后台线程访问已释放资源导致崩溃 | StopServer() 加 thread.Join(2s) 等待线程退出 |
| 3 | ChatManager 事件订阅时序竞争导致首帧消息丢失 | 改为公开 Init() 方法，由 NetworkTest 在启动后主动调用 |
| 4 | 广播不排除发送者导致远端客户端看到重复消息 | Broadcast 加 excludeId 参数 |
| 5 | ConnectionManager 本地客户端回调未参与排除逻辑 | Broadcast 加 includeLocal 参数控制 |
| 6 | 后台线程修改非线程安全字典 | clientToPlayer 加锁保护 |
| 7 | 聊天 Content 锚点设置错误导致不滚动 | 锚点固定到顶部，ContentSizeFitter + VerticalLayoutGroup |
| 8 | ChatManager 注册 OnServerClientDisconnected 缺失 | 断开时自动清理 clientToPlayer |
| 9 | NetworkManager 启动失败时状态未重置 | IsServer/IsClient 置 false |
| 10 | SocketException 导致 NetworkClient 接收线程永久退出 | 改为捕获后重试，不退出 |
| 11 | SocketException 导致服务端 ListenerLoop 退出 | 改为捕获后重试，不退出 |
| 12 | 服务端 OnServerDataReceived / OnServerClientConnected 在后台线程触发 | 加事件队列，主线程统一触发 |
| 13 | 服务端无客户端心跳导致空闲 5s 被踢 | 客户端加心跳保活（1Hz），超时改为 10s |
| 14 | ReliableChannel 序列号空洞导致所有可靠消息永久卡死 | 接收方 buffer 超 5 条跳过空洞 |

## 五、待实现（阶段三 ~ 六）

### 🔒 阶段三的线程约束

阶段三所有系统改造必须遵守以下规则：

1. **所有网络事件都在主线程触发**（已通过 LiteNetTransport 队列保证）
2. 在 `OnServerDataReceived` 和 `OnClientDataReceived` 中可以直接使用 Unity API
3. 但要注意：**事件处理函数不要长时间阻塞主线程**（单帧<16ms）
4. 高频消息（如位置同步）建议使用不可靠传输，且处理函数要足够轻量

## 六、线程安全设计

```
ListenerLoop (后台线程)                    NetworkClient.ReceiveLoop (后台线程)
  ├─ ConcurrentDictionary 操作 ← 安全       ├─ ConcurrentQueue.Enqueue ← 安全
  ├─ ConcurrentQueue.Enqueue ← 安全          └─ (数据排队等待主线程)
  └─ (数据排队等待主线程)                           ↓
        ↓                                Update() (主线程)
  Update() (主线程)                          ├─ clientReceiveQueue 出队
  ├─ serverReceiveQueue 出队                 ├─ OnClientDataReceived(主线程)
  │  └─ OnServerDataReceived(主线程)         └─ UI_Chat.AddMessage → Instantiate(主线程)
  ├─ serverEventQueue 出队                   
  │  └─ OnServerClientConnected(主线程)     
  └─ clientUpdate + serverUpdate            
```

**规则**：所有 `OnXxxReceived` / `OnXxxConnected` 事件都在主线程触发，事件处理函数可以直接调用 Unity API。

## 七、与 TCP 对比

| 功能 | ReliableChannel | TCP | 本项目是否需要 |
|------|----------------|-----|---------------|
| 可靠送达 | ✅ ACK + 重传 | ✅ 内置 | ✅ 必要 |
| 按序到达 | ✅ 乱序缓存 | ✅ 内置 | ✅ 必要 |
| 心跳保活 | ✅ 双向 1Hz | ✅ Keep-Alive | ✅ 必要 |
| 断开检测 | ✅ 10s 超时 | ✅ 内置 | ✅ 必要 |
| 流量控制 | ❌ 不需要 | ✅ 内置 | ❌ 消息量小，撑不爆 |
| 拥塞控制 | ❌ Steam 代劳 | ✅ 内置 | ❌ LAN + Steam 不需要 |
| 自适应超时 | ❌ 固定 200ms | ✅ 动态 RTT | ❌ LAN 固定参数足够 |

**结论**：ReliableChannel 已覆盖 TCP 在本项目的所有必要功能，不需要额外添加 TCP 连接。

## 十、核心原则

### 原则 1：不能破坏单机模式
所有网络代码加条件守卫：
```csharp
void Update() {
    if (NetworkManager.Instance != null && NetworkManager.Instance.IsClient && !IsServer)
        return;  // 远端客户端不跑逻辑
    stateMachine.UpdateActiveState();
}
```
单机时 `NetworkManager.Instance` 为 `null`，现有代码不受影响。

### 原则 2：自底向上，每阶段可测试
- 传输层已完成（LiteNetLib 库测试）
- 网络管理层已完成（NetworkManager/聊天）
- 阶段三开始后每个新系统单独验证

### 原则 3：先用 LAN 模式开发，Steam 最后接入
阶段一到三全部用 `LiteNetTransport` 开发。阶段四才换成 `SteamTransport`。

### 原则 4：源码编译，去 DLL
LiteNetLib 源码直接放在 `Assets/Scripts/LiteNetLib/` 下，由 Unity 编译。
避免 DLL 版本不一致问题，修改后无需手动复制。
