# 多人联机开发方案

> 类银河恶魔城 Unity 2D 动作RPG — 毕设项目  
> **网络方案**：自研 LiteNetLib（传输层）+ 自研 Unity 网络层（游戏对象同步）  
> **联机模式**：Listen Server（主机模式），纯单机模式保留  
> **传输切换**：自研 LiteNetLib（局域网/直连）↔ Steamworks（大厅/P2P）  
> **时间预算**：5 个月以上

---

## 二、关键设计决策

| 序号 | 决策 | 选择 |
|------|------|------|
| 1 | 传输抽象方式 | `IGameTransport` 接口 |
| 2 | RPC 风格 | 直接 PackMessage + Send / Dispatcher，不做额外封装层 |
| 3 | 位置同步 | 服务端快照 + 客户端插值（预测可选延迟） |
| 4 | 背包模型 | 简化版：各客户端管理自己背包，只广播变化 |
| 5 | 服务端AI | 是，Enemy 在服务端（主机）跑完整 FSM |
| 6 | 伤害计算 | 服务端执行，广播结果 |
| 7 | 客户端预测 | 第一阶段不做，第二阶段可选 |
| 8 | 断线重连 | 不实现（显示"主机已断开"即可） |
| 9 | 主机迁移 | 不实现 |
| 10 | 防作弊 | 有限——Listen Server 模式下信任主机 |

**目标**：把你现有的传输层库完善到能支持完整的 C/S + Host 模式。

#### 任务 1.1：实现 NetworkClient

**文件**：`LiteNetSolution/LiteNetLib/Connection/NetworkClient.cs`

服务端已有 `ConnectionManager`（管理多个客户端连接），客户端需要一个对应的连接管理器：

```csharp
public class NetworkClient
{
    public ConnectionState State { get; private set; }
    public event Action OnConnected;
    public event Action OnDisconnected;
    public event Action<byte[]> OnDataReceived;

    public void Connect(string host, int port);
    public void Disconnect();
    public void Send(byte[] data, bool reliable);
    public void Update();  // 驱动 ReliableChannel
}
```

**内部设计**：
- 一个 `UdpClient` 连接到服务端
- 一个 `ReliableChannel` 实例（每个客户端一个就够了）
- 后台线程轮询 UDP 接收，调用 `channel.OnRawDataReceived()`
- 发送时根据 `reliable` 参数走 `SendReliable` 或 `SendUnreliable`

**测试验证**：写一个集成测试，启动服务端 ConnectionManager + 客户端 NetworkClient，互相发 1000 条消息确认收发正确。

#### 任务 1.2：实现 HostMode（本机环回）

**文件**：`LiteNetSolution/LiteNetLib/Connection/NetworkClient.cs`（内增 Host 模式）

Listen Server 模式下，主机既运行服务端也运行客户端。客户端"连接自己"时不走 UDP，而是直接内存传递：

```csharp
// NetworkClient 新增
public bool IsLocalMode { get; private set; }

public void ConnectAsLocal()
{
    IsLocalMode = true;
    State = ConnectionState.Connected;
    // 不走 UDP，直接走本地队列
}

// ConnectionManager 新增
public void SendToLocalClient(byte[] data)
{
    localClientInbox?.Enqueue(data);
}
```

**设计要点**：
- `ConnectionManager` 在 Host 模式下维护一个 `localClientId`
- 当 `SendTo(localClientId, data)` 被调用时，不走 UDP，直接入本地队列
- `NetworkClient.Update()` 在本地模式下从队列取数据

#### 任务 1.3：定义 IGameTransport 接口

**文件**：`LiteNetSolution/LiteNetLib/IGameTransport.cs`

这是整个方案的**核心抽象**——所有上层代码依赖这个接口，不依赖底层传输实现：

```csharp
public interface IGameTransport
{
    // 服务端接口
    bool StartServer(int port);
    void StopServer();
    void SendToClient(int connectionId, byte[] data, bool reliable);
    void Broadcast(byte[] data, bool reliable, int excludeId = -1);

    // 客户端接口
    bool Connect(string address, int port);
    bool ConnectAsLocal();
    void Disconnect();
    void SendToServer(byte[] data, bool reliable);
    bool IsLocalConnection { get; }

    // 事件
    event Action<int> OnServerClientConnected;
    event Action<int> OnServerClientDisconnected;
    event Action<byte[]> OnServerDataReceived;
    event Action OnClientConnected;
    event Action OnClientDisconnected;
    event Action<byte[]> OnClientDataReceived;

    // 帧驱动
    void Update();

    // 状态
    bool IsServerRunning { get; }
    bool IsConnected { get; }
    bool IsHostMode { get; }
}
```

#### 任务 2.7：RPC 方式

**决策：手动 PackMessage + Send，不做 RPC 封装层。**

原因：现有 `MessageDispatcher` 已经完成了 RPC 的"接收→路由"部分。发送部分在客户端只有一处（`Transport.SendToServer`），在服务端也只有一处（`Transport.Broadcast` 或 `Transport.SendToClient`）。再包一层 `Rpc.SendToServer<T>` 没有实质简化。

**实际写法**：

```csharp
// ---- 客户端发送 ----
byte[] packet = MessageDispatcher.PackMessage(MSG_INPUT, new PlayerInputData { x = 1 });
NetworkManager.Instance.Transport.SendToServer(packet, false);

// ---- 服务端注册处理 ----
dispatcher.RegisterHandler<PlayerInputData>(MSG_INPUT, (clientId, msg) => {
    HandleInput(clientId, msg);
});

// ---- 服务端广播 ----
var evt = new DamageEvent { targetId = 5, damage = 50 };
byte[] packet = MessageDispatcher.PackMessage(MSG_DAMAGE, evt);
NetworkManager.Instance.Transport.Broadcast(packet, true);

// ---- 客户端注册处理 ----
clientDispatcher.RegisterHandler<DamageEvent>(MSG_DAMAGE, (msg) => {
    PlayHitEffect(msg);
});
```

**什么时候考虑封装？** 如果同一个消息类型在项目中会出现 10 次以上的 Pack+Send，才值得为它做自动化封装。目前阶段不需要预判。直接手动打包足够简单、足够灵活。

### 阶段三：游戏逻辑网络化（预计 5-7 周）

**目标**：把玩家控制、战斗、敌人 AI、背包等核心系统接入网络。

#### 3.1 总体原则

- **不改单机路径**：所有网络代码通过 `if (IsServer)` / `if (IsClient)` 分支嵌入，不破坏单机玩法
- 单机时 `NetworkManager.Instance == null`，网络代码不执行

#### 3.2 Listen Server 角色分工

| 系统 | 服务端(主机) | 远端客户端 |
|------|-------------|-----------|
| 玩家输入 | 读本地输入 | 发送输入 → 主机执行 |
| 位置计算 | 服务端跑物理 | 接收快照 → 本地插值 |
| 伤害计算 | ✅ 主机负责 | ❌ 不计算 |
| 敌人 AI | ✅ 主机跑 FSM | ❌ 不跑AI，只播放同步表现 |
| 战利品生成 | ✅ 主机 Random | ❌ 不生成，等通知 |
| 背包操作 | ✅ 主机验证后修改 | 发请求 → 主机验证 |
| 技能释放 | ✅ 主机验证冷却/消耗 | 发请求 → 主机验证 |
| 任务进度 | ✅ 主机判定 | ❌ 不判定 |
| 经验获得 | ✅ 主机计算 | ❌ 接收通知 |

## 五、核心原则

### 原则 1：不能破坏单机模式
所有网络代码加条件守卫：

### 原则 2：自底向上，每阶段可测试
- 阶段一完成 → 两个控制台程序能互发消息
- 阶段二完成 → 两个 Unity 实例能看到对方角色
- 阶段三完成 → 能联机打怪
- 每一阶段都有可演示的成果

### 原则 3：先用 LAN 模式开发，Steam 最后接入
阶段一到三全部用 `LiteNetTransport` 开发。阶段四才换成 `SteamTransport`。LAN 模式调试方便，无需 Steam API。

### 原则 4：Listen Server 的主要权衡
| 优点 | 缺点 |
|------|------|
| 不需要额外服务器成本 | 主机掉线 → 游戏结束 |
| 实现简单 | 主机延迟为0（比远端有优势） |
| 适合合作类独立游戏 | 主机能作弊（信任模型） |
